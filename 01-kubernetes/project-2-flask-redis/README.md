# Kubernetes Project 2 — Flask + Redis Multi-Container Application

## 📌 Overview

This project demonstrates how to deploy a multi-container application on Kubernetes using a Flask web application and Redis as the backend data store.

The project covers Kubernetes Deployments, Pods, Services, service discovery, environment variables, NodePort access, Docker image management, scaling, and rolling updates.

## 🧩 Application Components

### Flask Application

The Flask application provides the web interface and displays the visitor count. It connects to Redis through the Kubernetes Service name rather than using a Pod IP directly.

```text
REDIS_HOST=redis-service
```

### Redis

Redis stores the visitor count generated by the Flask application. Redis runs inside the Kubernetes cluster and is exposed internally through a ClusterIP Service, so it is not directly exposed to the internet.

## ☸️ Kubernetes Configuration

A dedicated namespace was created:

```text
flask-redis
```

Redis is deployed through `redis-deployment` and listens on port `6379`.

Redis is exposed internally through:

```text
redis-service:6379
```

Kubernetes DNS resolves `redis-service` to the Redis Service, providing stable service discovery even when Pod IP addresses change.

The Flask application is deployed through `flask-deployment` with an initial two replicas.

## 🐳 Docker Image

The Flask application was packaged as a Docker image and pushed to Docker Hub:

```text
10messiaws/flask-k8s-app:1.0
```

Kubernetes pulls the image from Docker Hub when creating the Flask Pods.

## 🌐 Flask Service

The Flask application is exposed externally through `flask-service` using NodePort:

```text
30081
```

Application access:

```text
http://<EC2-PUBLIC-IP>:30081
```

An AWS EC2 Security Group inbound rule was configured to allow TCP traffic on port `30081`.

## 🔗 Kubernetes Networking & Service Discovery

Kubernetes provides cluster networking automatically, so a manually created Docker network is not required.

The Flask application communicates with Redis using the stable Service name:

```text
REDIS_HOST=redis-service
```

This avoids depending on the changing IP address of the Redis Pod.

## 📈 Scaling

The Flask Deployment initially ran with two replicas and was scaled to four:

```bash
kubectl scale deployment flask-deployment --replicas=4 -n flask-redis
```

Final application state:

```text
4 Flask Pods
1 Redis Pod
```

This demonstrates horizontal scaling at the Kubernetes Deployment level.

## 🔄 Rolling Updates

The Flask Deployment also demonstrates Kubernetes rolling updates. The application image can be updated through the Deployment, allowing Kubernetes to gradually replace existing Pods while maintaining application availability.

## 🔄 Application Flow

```text
Browser
   │
   ▼
Flask NodePort Service
   │
   ▼
Flask Deployment
   ├── Flask Pod 1
   ├── Flask Pod 2
   ├── Flask Pod 3
   └── Flask Pod 4
   │
   ▼
Redis ClusterIP Service
   │
   ▼
Redis Pod
```

When a user accesses the application, the request reaches Flask through the NodePort Service. Flask processes the request and communicates with Redis through the Redis Service. Redis increments and stores the visitor count, which is then displayed by Flask.

2. Use Deployments to manage Pods.
3. Use ClusterIP for internal communication.
4. Use NodePort for external access.

## 🏁 Outcome

The Flask + Redis application was successfully deployed on Kubernetes. The Flask application was accessible externally through NodePort, while Redis remained internally accessible through ClusterIP. The visitor count was maintained by Redis, and the Flask application was successfully scaled from two to four replicas.

This project provided practical experience with deploying a real multi-component application and understanding how Kubernetes Services, Deployments, networking, service discovery, container images, scaling, and rolling updates work together.
